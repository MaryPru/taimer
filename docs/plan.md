# План работы

План S0–S4 составлен в начале работы по тексту задания. S5 добавлен после S4: в нём закрыто то, что выявила сверка результата с заданием. Каждый спринт заканчивается рабочим состоянием и зелёными тестами. Задание спринта (цель, задачи, проверки, критерий готовности) служило спецификацией, по которой модель писала код и тесты. Ход работы и результаты по спринтам: [`ai-log.md`](ai-log.md).

## Требования и где они закрыты

| Требование | Спринт | Чем проверяем |
|---|---|---|
| Добавление сотрудников | S1 | Тест: сотрудник создаётся, пустое имя отклоняется с 400 |
| Старт и стоп таймера с описанием задачи | S1 | Тест: старт, затем стоп дают одну запись с длительностью; без описания задачи старт отклоняется |
| Повторный запуск таймера | S1 | Тесты: второй старт при идущем таймере даёт 409 и не создаёт запись; старт после стопа создаёт новую запись |
| Записи и общее время каждого сотрудника за период | S2 | Тесты: итог по сотруднику, запись через границу периода учитывается только внутри него, идущий таймер считается до текущего момента |
| Пустой отчёт | S2 | Тест: период без записей возвращает нулевые итоги и пустые списки; в интерфейсе понятное пустое состояние |
| Сохранение данных после перезапуска | S0, S4 | Тест: закрываем и заново открываем файл базы, сотрудники и записи на месте, идущий таймер продолжает идти |
| Простой интерфейс | S3, S5 | Ручной чек-лист сценариев, тесты интерфейса |
| Только вымышленные данные | S4 | `npm run seed` с придуманными сотрудниками и задачами |
| README: запуск, ИИ-инструменты, примеры промптов, найденные ошибки | S4, S5 | Собирается из журнала `docs/ai-log.md` |

## Правила предметной области

- У сотрудника не больше одного идущего таймера. Таймеры разных сотрудников независимы.
- Описание задачи обязательно, от 1 до 200 символов. Имя сотрудника от 1 до 100 символов, пробелы по краям обрезаются.
- Время хранится в UTC. Границы периода считает браузер в своём часовом поясе: начало дня «с» и начало дня, следующего за «по».
- Даты периода принимаются только в ISO 8601 с явным часовым поясом, например `2026-11-02T00:00:00+03:00`. Дата без пояса и несуществующие даты вроде 30 февраля дают 400.
- Запись, которая пересекает границу периода, попадает в отчёт только своей частью внутри периода. Сама запись отдаётся целиком, обрезается только длительность.
- Идущий таймер в отчёте считается до текущего момента и помечается как активный.
- В отчёте есть все сотрудники; у кого не было работы, показан 0:00. Если записей за период нет совсем, показывается пустое состояние.

## Спринты

Порядок важен: интерфейс строится поверх уже протестированного API, а README пишется, когда есть что рассказать.

### S0. Каркас проекта (1:00)

**Цель:** проект ставится и запускается одной командой, база создаётся с нужной схемой, тесты зелёные.

**Задачи**
- ESM, TypeScript в строгом режиме.
- Структура `src/server`, `src/web`, `src/shared`, `tests`.
- Скрипты `dev`, `build`, `start`, `test`.
- `db.ts` с миграцией схемы, маршрут `/api/health`.
- Журнал `docs/ai-log.md`.

**Проверки**
- Схема создаётся на пустой базе, повторный запуск миграции ничего не ломает.
- `/api/health` отвечает 200.

**Готово, когда** `npm start` отдаёт страницу на `:3000`, `npm test` проходит, файл `data/taimer.db` появляется после первого запуска.

### S1. Сотрудники и таймер (2:00)

**Цель:** API для добавления сотрудников и запуска с остановкой таймера, с понятными ошибками.

**Задачи**
- Сервис сотрудников: создать, список с идущим таймером.
- Сервис таймера: старт и стоп, проверка «уже идёт» и «не запущен».
- Маршруты и единый формат ошибки `{ error, message }`.
- Перевод нарушения уникального индекса в ответ 409.

**Проверки**
- Создание сотрудника, пустое имя даёт 400.
- Старт и стоп дают одну запись с длительностью.
- Повторный старт при идущем таймере: 409, запись одна.
- Старт после стопа: вторая запись.
- Стоп без идущего таймера: 409.
- Несуществующий сотрудник: 404.
- Два сотрудника работают одновременно.

**Готово, когда** все сценарии таймера покрыты тестами и проходят.

### S2. Отчёт за период (1:30)

**Цель:** записи и общее время каждого сотрудника за выбранный период, включая пустой отчёт.

**Задачи**
- Маршрут `/api/report` с валидацией `from` и `to`.
- Выборка записей, пересекающих период.
- Обрезка длительности по границам, идущий таймер до текущего момента.
- Итоги по сотрудникам и общий итог.

**Проверки**
- Пустой отчёт: нулевые итоги, пустые списки.
- Запись внутри периода считается целиком.
- Запись через полночь обрезается по границе.
- Идущий таймер считается до «сейчас».
- `from` позже `to`: 400.

**Готово, когда** отчёт за любой период совпадает с ручным подсчётом в тестах.

### S3. Интерфейс (2:30)

**Цель:** простой экран, на котором можно пройти все сценарии задания без Postman.

**Задачи**
- Блок «Сотрудники»: форма добавления и список.
- У каждого сотрудника поле задачи, кнопка «Старт» или «Стоп», живой счётчик.
- Блок «Отчёт»: сегодня, неделя, месяц или свой период; таблица записей и итоги.
- Состояния: пусто, загрузка, ошибка; кнопка блокируется на время запроса.

**Проверки**
- Тесты форматирования длительности и расчёта границ периода.
- Ручной чек-лист: добавить, запустить, перезагрузить страницу, остановить, посмотреть отчёт.

**Готово, когда** весь чек-лист проходится в браузере, а после перезагрузки страницы идущий таймер продолжает считать.

### S4. Стабилизация и сдача (1:30)

**Цель:** доказать сохранность данных, вычистить ошибки и описать работу так, чтобы её можно было защитить.

**Задачи**
- Тест перезапуска на файле базы.
- `npm run seed` с вымышленными сотрудниками и задачами.
- Ревью кода с ИИ (`/code-review`), разбор и исправление находок.
- README: запуск, стек, ИИ-инструменты и модели, примеры промптов, найденные ошибки, тесты.
- Финальная проверка из чистой копии.

**Проверки**
- После закрытия и открытия базы данные на месте.
- Идущий таймер переживает перезапуск сервера.
- Из чистой копии `npm install && npm start` работает.

**Готово, когда** README отвечает на все пункты задания, а каждая упомянутая в нём ошибка подтверждена тестом или проверкой в браузере.

### S5. Подготовка к сдаче (2:00)

**Цель:** сделать решение проверяемым: план и примеры промптов в репозитории, тесты интерфейса, запуск на любой поддерживаемой версии Node.

**Задачи**
- `docs/plan.md`: этот план в репозитории.
- Примеры промптов в README.
- Тесты интерфейса (React Testing Library) на настоящем API: полный цикл, повторный старт, пустой отчёт, тёзка, вкладки.
- Совместимость: проверка на Node 24 и 26, понятное сообщение на неподходящей версии.
- Скриншоты в README: компьютер и телефон.

**Проверки**
- `npm test` зелёный вместе с тестами интерфейса.
- Чистая копия на Node 22, 24 и 26: `npm ci`, тесты, `npm start`.
- На неподходящей версии Node установка останавливается с понятным сообщением.

**Готово, когда** проверяющий видит результат до запуска, а каждое утверждение README можно проверить по репозиторию.

## Как проходит спринт

1. **Задание.** Цель спринта, правила предметной области и критерий готовности из этого плана.
2. **Код и тесты.** Модель пишет тесты на сценарии из плана и реализацию.
3. **Проверка.** Дифф, `npm test`, проверка типов, запросы к собранному серверу, проверка в браузере.
4. **Ревью.** Модель ищет ошибки, решение о том, что править, принимается по результатам воспроизведения.
5. **Журнал.** Решения и найденные ошибки записываются в `docs/ai-log.md`.
