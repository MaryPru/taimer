**Цель:** проект ставится и запускается одной командой, база создаётся с нужной схемой, тесты зелёные.

## Спринт 1. Сотрудники и таймер

**Цель:** API для добавления сотрудников, запуска и остановки таймера, с понятными ошибками и тестами на все сценарии таймера.

### Запрос

> делай спринт 1

Задачи, правила предметной области и список проверок модель взяла из плана.

### Что сделано

- `src/shared/types.ts`: типы запросов и ответов, лимиты длины, коды ошибок.
- `src/server/errors.ts`: `AppError` и единый формат ответа `{ error, message }` для своих ошибок, ошибок валидации, ошибок разбора тела и неизвестных маршрутов.
- `src/server/employees.ts`, `src/server/timer.ts`: сервисы; `src/server/routes.ts`: маршруты.
- Тесты получают управляемые часы `TestClock`, поэтому длительности проверяются точно, без `sleep`.

### Решения

- **Повторный старт ловит база, а не код.** Перед вставкой нет `SELECT` «идёт ли таймер»: между проверкой и вставкой мог бы проскочить второй запрос. Нарушение индекса `one_running_timer` (`errcode` 2067) переводится в 409 `TIMER_ALREADY_RUNNING`.
- **Стоп пишет `max(now, started_at)`.** Если системные часы ушли назад, запись получает нулевую длительность, а не 500 от `CHECK (ended_at >= started_at)`.
- **Сначала проверка содержимого, потом существования.** Пустое описание задачи даёт 400 даже для несуществующего сотрудника.
- **`Content-Type: application/json` клиент ставит только при наличии тела:** на этот заголовок с пустым телом Fastify отвечает 400, а у стопа таймера тела нет.

### Что проверили

- `npm run typecheck`, `npm test`: 41 тест.
- **Проверка тестов поломкой кода.** Вернули приведение типов: упали 3 теста. Сделали индекс `one_running_timer` неуникальным: упали 3 теста на повторный запуск.
- Прогон через настоящий HTTP на собранном сервере с отдельной базой: старт, повторный старт 409, стоп, повторный стоп 409, чужой id 404.

### Ошибки в коде

- **Fastify молча приводил типы в теле запроса.** `{ "name": true }` создавал сотрудника с именем `"true"`, `{ "name": 123 }` сотрудника `"123"`, `{ "task": 42 }` запускал задачу `"42"`. Найдено ручной проверкой граничных случаев. Причина в настройке Ajv по умолчанию (`coerceTypes`). Исправление: `coerceTypes: false`; `id` в пути проверяется как строка шаблоном `^[1-9][0-9]{0,14}$` и переводится в число в маршруте. Тесты на число, `true`, `null`, `01`, `1e3` и 16-значный id.

## Спринт 2. Отчёт за период

**Цель:** записи и общее время каждого сотрудника за выбранный период, включая пустой отчёт.

### Запрос

> делай спринт 2

### Что сделано

- `GET /api/report?from=&to=`: все сотрудники с итогами и записями, общий итог, момент расчёта `generatedAt`.
- `src/server/period.ts`: строгий разбор дат (`parseInstant`, `parsePeriod`) и расчёт доли записи в периоде (`shareInPeriod`). Это чистые функции, у них отдельные модульные тесты.
- `src/server/report.ts`: SQL отбирает кандидатов с запасом на границах, точное решение принимает `shareInPeriod`.

### Решения

- **Период — полуинтервал `[from, to)`.** Запись, которая заканчивается ровно в полночь, не попадает в следующие сутки. Запись нулевой длительности относится к периоду, в котором началась, и не теряется на границе.
- **Запись отдаётся целиком, обрезается только `durationMs`.** В отчёте видно настоящее начало и конец задачи, а в итог идёт только время внутри периода.
- **В отчёте есть все сотрудники.** Те, кто не работал, показаны с нулём.
- **Даты принимаются только в ISO 8601 с явным часовым поясом.** Сутки считает браузер в своём поясе, сервер работает с моментами времени и не зависит от пояса машины.

### Что проверили

- `npm test`: 94 теста (разбор дат, пересечения, отчёт через API).
- **Проверка тестов поломкой кода**, 7 мутаций, все пойманы:

  | Мутация | Упало тестов |
  |---|---|
  | длительность не обрезается по границам | 5 |
  | границы периода включительные | 4 |
  | идущий таймер не считается | 3 |
  | записи не сортируются по началу | 1 |
  | итог сотрудника не копится | 5 |
  | календарь не учитывает длину месяца | 5 |
  | любой год, кратный 4, високосный | 1 |

- HTTP: отчёт за сегодня в поясе `+02:00` с идущим таймером, незакодированный `+` даёт 400 с подсказкой, пустой период даёт нулевые итоги.

### Ошибки в коде

1. **`Date.parse` молча принимает неверные периоды.** Перед реализацией модель проверила, как V8 разбирает граничные строки:
   - `2026-02-30` становится 2 марта;
   - `2026-11-02` читается как полночь UTC;
   - `2026-11-02T00:00:00` читается как полночь в поясе сервера;
   - незакодированный `+` в query-строке становится пробелом, и `+03:00` пропадает.

   Разбор сделан строгим шаблоном с обязательным поясом, проверкой календаря и отдельной подсказкой про `%2B`. На каждый случай есть тест.
2. **Проверка календаря через `Date.UTC` ошибалась на годах 0–99:** он считает их как 1900–1999, поэтому `0000-02-29` отклонялся бы. Заменена явным расчётом дней в месяце, добавлены тесты на 2000 и 2100 годы.

## Спринт 3. Интерфейс

**Цель:** простой экран, на котором можно пройти все сценарии задания без Postman.

### Запрос

> делай спринт 3

### Что сделано

- `src/shared/time.ts`: формат «ч:мм:сс», локальное время с явным смещением для API, разбор `<input type="date">`, границы периода, пресеты «сегодня / неделя / месяц», досчёт идущих таймеров в отчёте. Это чистые функции с модульными тестами.
- `src/web`: `api.ts` (типизированные запросы и ошибки), `useNow` (один тикающий таймер на всё приложение), компоненты `EmployeeForm`, `EmployeeRow`, `PeriodPicker`, `ReportView`.
- Состояния интерфейса: пусто, загрузка, ошибка API у конкретного сотрудника, баннер «сервер не отвечает» с кнопкой «Повторить», кнопки блокируются на время запроса.

### Решения

- **Период строится в поясе браузера по календарным дням**, а не прибавлением 24 часов. В дни перевода часов сутки длятся 23 или 25 часов, тесты проверяют это на поясе Europe/Berlin.
- **Неделя считается с понедельника по воскресенье.**
- **После любого действия список сотрудников перечитывается**, в том числе после ошибки: таймер могли запустить в другой вкладке.
- **Ответ на устаревший запрос отчёта отбрасывается:** быстрые переключения периода не перепутают данные.
- **Параметры периода кодируются через `URLSearchParams`**, поэтому `+` в часовом поясе доходит до сервера.

### Что проверили

- `npm test`: 127 тестов.
- **Ручной чек-лист в Chrome** на собранном приложении с отдельной базой:
  - пустые состояния;
  - добавление двух сотрудников;
  - старт и живой счётчик, отчёт тикает синхронно;
  - перезагрузка страницы, таймер продолжает считать;
  - повторный старт, когда таймер уже запущен из другого места: понятная ошибка 409 и обновлённый список;
  - стоп, в отчёте появляется время окончания;
  - «Эта неделя» даёт 02.11–08.11;
  - дата «с» позже «по» даёт подсказку;
  - пустой период даёт «записей нет»;
  - остановка сервера показывает баннер;
  - перезапуск сервера: данные на месте, идущий таймер продолжает считать, «Повторить» восстанавливает экран;
  - ошибок в консоли нет.

### Ошибки в коде

1. **Итог отчёта не сходился с суммой строк:** 0:00:36 + 0:02:56 давали «Итого 0:03:33» вместо 0:03:32. Найдено при сверке цифр в браузере. Причина: время хранилось в миллисекундах, каждая строка округлялась вниз отдельно, и дробные части двух строк в сумме давали лишнюю секунду. Исправление: сервер фиксирует старт, стоп и «сейчас» с точностью до секунды, доля записи в периоде округляется до секунды, живой досчёт прибавляет целые секунды. На каждое из трёх мест есть тест.
2. **Ошибка «сервер не отвечает» показывалась трижды:** в баннере, у сотрудника и в отчёте. Теперь сетевые ошибки показывает только баннер, а у сотрудника и в отчёте остаются ошибки API (409, 400).

## Проверка интерфейса в браузере

### Запрос

> проверь в браузере недочёты

### Как проверяли

Отдельная база с вымышленными данными на граничные случаи:
- 10 сотрудников, в том числе составное имя через дефис и слово из 70 букв без пробелов;
- задача со ссылкой без пробелов;
- записи за прошлые дни и через полночь;
- таймер, идущий третьи сутки.

Узкий экран проверяли в рамке `<iframe>` шириной 390 px: медиазапросы в ней срабатывают по ширине рамки. Тёмную тему проверяли, подставив её переменные. Фокус проверяли через `document.activeElement` после действий с клавиатуры.

### Найдено и исправлено

1. **Дата и время в таблице записей ломались на две строки.** Начало и конец сведены в одну строку под задачей: «02.11, 08:00 – 09:15». Дата у конца пишется, только если запись перешла через местную полночь (`formatEntrySpan`).
2. **На телефоне таблицы отчёта уходили в горизонтальную прокрутку, а длинное слово в имени раздвигало страницу.** Таблицы переведены на фиксированную раскладку (`table-layout: fixed`) с явной шириной узких колонок, длинные слова переносятся внутри своей ширины.
3. **Фокус клавиатуры терялся после «Добавить», «Старт» и «Стоп»:** поле блокируется на время запроса и теряет фокус. Теперь после добавления курсор остаётся в поле имени, после старта фокус на «Стоп» той же строки, после остановки в поле задачи. Весь цикл проходится одной клавиатурой.
4. **Ошибка под строкой сотрудника оставалась, когда уже была неверна:** таймер остановили в другой вкладке, а под строкой всё ещё было «Таймер уже запущен». Ошибка привязывается к идущей записи, при которой получена, и пропадает, когда запись меняется.

Отдельно на решение вынесены четыре вопроса логики времени. Все они решены на следующем этапе.

## Доработки логики времени и вкладки на телефоне

### Запрос

> исправь эти моменты, а на телефоне сделай сотрудников и отчёт вкладками, чтобы было удобнее

### Что сделано

1. **Забытый таймер.** С 12 часов (`LONG_RUNNING_HOURS`, `isLongRunning`) часы в строке сотрудника становятся оранжевыми, под строкой появляется «Таймер идёт больше 12 часов. Возможно, его забыли остановить». В отчёте метка «идёт» сменяется на «идёт больше 12 ч». Порог 12 часов, а не сутки: забытый с вечера таймер виден уже утром.
2. **«Сегодня» после полуночи.** Отчёт хранит выбор периода (`PeriodSelection`: пресет или свои даты), а не даты. Даты пресета считаются от «сегодня» из хука `useToday`. Хук ставит таймер до следующей местной полуночи (`msUntilNextDay`, в ночь перевода часов до неё 23 или 25 часов) и перепроверяет день при возвращении на вкладку: таймер в спящей вкладке может опоздать. Свои даты при смене дня не трогаются.
3. **Год в датах отчёта** пишется, только если он не текущий: «31.12.2025, 21:00 – 01.01, 01:00».
4. **Тёзки.** Пока имя набирают, форма сверяет его со списком без учёта регистра и лишних пробелов, «ё» и «е» считаются одной буквой (`findNamesake`). При совпадении появляется предупреждение, а кнопка меняется на «Добавить ещё одного»: тёзки в компании бывают, поэтому совпадение не запрещается. Сервер схлопывает повторные пробелы внутри имени.
5. **Вкладки на узком экране.** До 860 px, где панели встают в одну колонку, появляются вкладки «Сотрудники / Отчёт» (`Tabs`, `useMediaQuery`) по образцу WAI-ARIA: `tablist`/`tab`/`tabpanel`, `aria-selected`, в обходе по Tab только выбранная вкладка, стрелки и Home/End переключают вкладки. На вкладке сотрудников счётчик идущих таймеров. Вкладки прилипают к верху экрана. Обе панели остаются смонтированными: таймеры тикают, отчёт не перезагружается при переключении.

### Решения

- Предупреждение о тёзке показывается в области `role="status"`, которая есть на странице всегда: если область появляется вместе с текстом, экранный диктор может её не прочитать.
- Роли вкладок ставятся только на узком экране. На широком панели стоят рядом, и `tabpanel` без видимого списка вкладок вводил бы в заблуждение.
- Панель скрывается атрибутом `hidden`, для него в CSS `display: none !important`: иначе `display: flex` у `.panel` показал бы скрытую вкладку.

### Что проверили

- `npm run typecheck`: 0 ошибок. `npm test`: 150 тестов. Новые тесты: год в датах и запись через Новый год, порог 12 часов, время до полуночи в ночь перевода часов, переход пресета на новый день, поиск тёзок, схлопывание пробелов на сервере.
- Проверка поломками новых функций: 9 мутаций, 8 пойманы тестами. Девятая показала, что проверка пустого имени в `findNamesake` лишняя (пустых имён у сотрудников не бывает), её убрали.
- В Chrome:
  - предупреждения и оранжевые часы у таймеров дольше 12 часов, метки в отчёте;
  - тёзка «  анна   тестова» вызывает предупреждение, сохраняется «анна тестова», фокус остаётся в поле;
  - год у прошлогодней даты;
  - полночь: время страницы подменено на «за 2 секунды до полуночи», через 2 секунды «Сегодня» перешло на следующий день; свои даты при смене дня не изменились;
  - вкладки в рамке 390 px: клавиатура, прилипание при прокрутке, нет горизонтальной прокрутки, светлая и тёмная тема;
  - переход 390 → 1000 → 390 px: на широком экране вкладки и их роли исчезают, на узком возвращаются с запомненной вкладкой;
  - ошибок в консоли нет.

### Решения

- **Тесты интерфейса работают с настоящим сервером.** `fetch` направлен в `app.inject()` приложения с базой в памяти (`tests/web/harness.ts`), ответы не подменяются. Тест проходит и клиентский, и серверный код, а данные для сценария готовятся теми же вызовами API, что и в тестах сервера.
- **Два проекта Vitest:** `api` в окружении Node и `web` в jsdom. Для `web` своё окружение `tests/web/jsdom-node.ts`: DOM от jsdom, но модули собираются как для Node. Стандартное окружение jsdom собирает модули как для браузера и не пропускает `node:sqlite`, который нужен серверу внутри теста.
- **Диапазон версий Node** взят из зависимостей: Vitest поддерживает `^22.12 || ^24 || >=26`, jsdom `^22.13 || >=24`, `node:sqlite` без флага есть с 22.13. Итог: `^22.13.0 || ^24.0.0 || >=26.0.0`. С `engine-strict` неподходящая версия останавливает `npm install` и `npm ci` ошибкой `EBADENGINE` с нужной и текущей версиями. Без него npm только предупреждает, а сервер падает уже при запуске.
- **`allowScripts` для esbuild.** npm 11.19 и новее, который идёт с Node 24 и 26, не запускает скрипты установки без разрешения. Единственный такой скрипт в зависимостях, `postinstall` у esbuild, разрешён в `package.json`: установка ведёт себя так же, как на npm из Node 22, и проходит без предупреждений.
- **Скриншоты сняты через протокол DevTools** с эмуляцией экрана 390 px. У окна headless Chrome есть минимальная ширина, и при обычном запуске вёрстка шла бы на ширине больше телефонной. Данные для снимков из `npm run seed`.
